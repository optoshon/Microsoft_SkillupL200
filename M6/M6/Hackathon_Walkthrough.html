What exactly are we building?

We are not building a generic writing assistant. We are building a bounded proposal copilot for the financial domain. The assistant must handle two primary modes: a user may provide a template, or may provide only a request. In both cases, the system must draft a structured proposal using retrieval from a proposal database and a controlled generation workflow.

The product boundary

If the user provides a template, the system should prioritize that template and treat retrieval as supportive. If the user does not provide a template, the system should retrieve a suitable financial proposal structure from the knowledge base. If the request is non-financial and no template is provided, the system must decline gracefully instead of pretending to have unsupported domain coverage.

What success looks like

The final output should feel like a serious consulting or enterprise proposal. It should include clear sections, strong financial-domain tone, realistic governance language, an implementation plan, risks and assumptions, and a coherent solution approach. It should not read like a chatbot answer or a generic AI pitch.

End-to-end workflow

The system should reason through the proposal-generation process instead of jumping directly to a final answer. These are the core stages the workflow should pass through.

1

Receive request

Accept the proposal need, RFP-like description, or business requirement. Optionally accept a user template.

2

Route the path

Determine whether a template exists and whether the request is inside the supported financial domain.

3

Retrieve context

Pull the right documents from the knowledge base: structure guides, full proposals, section templates, and approach patterns.

4

Draft proposal

Generate a structured proposal using the selected path, retrieved context, and the requested use case.

5

Evaluate and revise

Check for missing mandatory sections or weak areas, then insert or refine sections before producing the final output.

Three required system behaviors

These three branches make the hackathon task easy to explain and easy to judge. They also create strong demo moments.

Template-first path

User provides a template

The system must preserve the supplied structure as the primary basis for drafting. It should then compare the template against the expected financial proposal structure, detect missing or weak sections, and use retrieval to suggest or generate those missing sections without breaking the user’s structure.

Knowledge-base path

No template, financial request

The system must retrieve the best-matching financial proposal materials from the internal knowledge base, choose the right structure, select relevant section templates and approach language, and generate a full proposal grounded in the stored corpus.

Boundary path

No template, non-financial request

The system must decline gracefully. It should clearly state that the current knowledge base supports financial-domain proposal generation only, instead of hallucinating capability or applying irrelevant internal templates.

What goes into the knowledge base?

The database is not a random document dump. It is a curated proposal corpus built to improve retrieval quality. The assistant should retrieve different kinds of documents at different stages of the workflow.

Core control documents

Mandatory structure guideDefines what a complete financial proposal should contain. This powers missing-section detection.
Style and writing guideControls tone, clarity, business realism, and anti-fluff behavior.
Approach and architecture patternsProvides reusable solution patterns so every proposal does not sound architecturally identical.

Generation documents

Full proposal samplesUsed for flow, tone, sequencing, and section-level language patterns.
Section templatesUsed for precise insertion or repair of executive summaries, risks, implementation, solution sections, and more.
Commercial and next-step languageUsed to keep final proposals complete even when pricing specifics are not available.

Important principle

Retrieval should be stage-specific. For a first draft, retrieve high-level structure and one or two full examples. For a missing section, retrieve the exact section template. For architecture language, retrieve the approach-pattern document rather than stuffing the whole database into one prompt.

Where the “agentic” part becomes visible

This should not look like a single long prompt hidden behind a UI. The system should make intermediate decisions that are understandable and explainable.

Routing

The assistant should determine whether a template exists, whether the request is financial, and which generation path should be used.

Gap analysis

The assistant should compare user-supplied structure against the mandatory financial proposal structure and identify what is missing.

Selective retrieval

The assistant should choose the right retrieval source based on context: proposal examples, section templates, or approach patterns.

Approach selection

The assistant should select a fitting architecture narrative based on the use case rather than reusing the same technical language everywhere.

Evaluation

The assistant should assess whether the draft feels complete, realistic, and aligned with financial-domain expectations.

Revision

The assistant should revise weak sections or add missing ones such as Risks, Governance, or Implementation Plan before returning the final proposal.

Suggested system architecture for the MVP

Keep the build simple. The goal is not to create an overbuilt agent society. It is to create a clear and convincing workflow.

Minimum components

A router or planner decides the path. A retriever fetches relevant proposal documents. A drafter writes the proposal or target section. An evaluator checks for completeness and quality. A reviser inserts or rewrites missing sections if needed.

What not to overbuild

You do not need a perfect parser for every file format, deep memory, complex reranking, polished enterprise UI, or exact pricing estimation. A small but strong workflow is better than a broad and fragile one.

Recommended 4-hour build plan

This keeps the team focused on what judges will actually notice: grounded proposal quality, visible retrieval, and smart control flow.

Hour 1
Set up the corpus and retrievalLoad the financial proposal documents into a vector store or lightweight retrieval system. Confirm that the right documents can be fetched for general proposal generation and for section-specific prompts.
Hour 2
Implement routing and template logicAdd logic for template present versus absent, financial versus non-financial, and path selection. Include comparison against the mandatory financial structure guide.
Hour 3
Draft and reviseGenerate the first full draft, then add evaluation logic for missing mandatory sections such as Risks or Implementation Plan. Plug in section-level retrieval for revision.
Hour 4
Polish the demoPrepare two successful end-to-end examples and one graceful refusal path. Add visible logs or messages that show the system’s intermediate decisions and retrieval choices.

What teams should deliver

A working prototype is more important than a perfect product. The deliverables should show that the core logic works and that the team understands why this is an agentic RAG problem.

Mandatory deliverables

  • A working proposal-generation flow with retrieval.
  • Support for both template-first and no-template financial flows.
  • Graceful refusal for unsupported no-template non-financial requests.
  • A structured final proposal output.
  • A short demo showing at least one successful end-to-end case.

Strong bonus deliverables

  • Visible logs showing routing, retrieval, and revision decisions.
  • Section-aware insertion of missing mandatory blocks.
  • Selection of different architecture narratives for different use cases.
  • Simple UI for walking judges through the workflow.
  • An evaluator that explains why a revision was triggered.

How the hackathon should be judged

The judging should reward quality of workflow and honesty of system behavior, not just flashy visuals.

Routing quality

Did the system correctly choose between template-first, KB-first, and graceful refusal paths?

Retrieval relevance

Did the system retrieve genuinely useful proposal content rather than using RAG as decoration?

Proposal realism

Does the final proposal sound professional, structured, and financially credible?

Agentic behavior

Are intermediate decisions visible and meaningful, especially around missing-section detection and revision?

Control and honesty

Does the system respect its domain boundary instead of hallucinating unsupported capability?

Best demo story for the walkthrough

A strong presentation should not just show one long successful generation. It should show the product boundary, the value of retrieval, and the reason the system is called agentic.

Scenario 1

Financial proposal request without a template. The system retrieves structure and examples from the knowledge base and drafts a complete proposal.

Scenario 2

Financial proposal request with a partial template. The system detects that Risks and Implementation are missing, retrieves section templates, and inserts them intelligently.

Scenario 3

Non-financial request without a template. The system declines gracefully and explains the supported boundary. This demonstrates controlled behavior.

The winning story is simple: this assistant does not just write. It reasons about structure, retrieves relevant proposal knowledge, respects user templates, and refuses unsupported cases honestly.

What this hackathon is not

Stating the non-goals helps everyone stay focused and reduces wasted effort on things that judges will not prioritize in a 4-hour build.

Not required

Full enterprise deployment, perfect DOCX support, universal multi-domain coverage, exact pricing logic, polished account management, and heavy infrastructure are all out of scope for this event.

What matters instead

Strong retrieval, clear logic, a believable proposal, clean handling of templates, and a visible explanation of why the workflow is agentic and grounded.
