Hackathon Handout: Front Agent + Agentic RAG (Text-Only)

Build a chat assistant with two core parts: a Front Agent (with conversation memory) that produces a Retrieval Plan, and an Agentic RAG loop that can retrieve, evaluate sufficiency, refine, retrieve again (max 2 iterations), and answer with citations.

Text-only retrieval Memory + planning 2-pass agentic loop Citations by chunk ID
User → FrontAgent(memory) → AgenticRAGLoop(retrieve/eval/refine) → Answer

What you are building

This is a practical build: simple components, clear interfaces, and a working end-to-end demo. Start with text retrieval. If you want to extend later, that’s optional.

Front Agent

Uses memory + user query to produce a structured Retrieval Plan.

Agentic RAG

Retrieve → evaluate sufficiency → refine → retrieve again → synthesize with citations.

Definition of “Done” (Deliverables)

Must demonstrate

  • n-turn conversation (you choose n) where memory affects the plan or the answer.
  • At least one query that triggers iteration 2 (refined retrieval).
  • Final answer includes citations using retrieved chunk IDs (e.g., [C2] [C6]).

Must submit

  • An entry point: run_chat.py (CLI) or app.py (simple UI).
  • A per-query trace.json that captures the plan, retrieval results, evaluator verdict, and final answer.
  • Readable outputs (logs or saved artifacts) suitable for explaining your system during the demo.
Constraint: cap the Agentic RAG loop to 2 iterations. If iteration 2 still isn’t sufficient, provide the best possible answer and clearly state limitations.

Component Contracts (Interfaces)

1) Memory Model (minimal and sufficient)

Keep memory lightweight: store recent turns plus a rolling summary. The goal is continuity, not perfect recall. 

{
  "history": [
    {"role": "user", "content": "…"},
    {"role": "assistant", "content": "…"}
  ],
  "summary": "Short rolling summary of the conversation so far.",
  "facts": {
    "optional_user_preferences": "e.g., 'keep answers brief', 'prefer bullet points'"
  }
}

2) Front Agent (Memory + Planning)

The Front Agent takes the user message + memory and outputs a Retrieval Plan. This plan is what your RAG loop will execute.

Inputs

{
  "user_message": "What is the sick leave carry forward limit?",
  "memory": { "...": "see memory model above" }
}

Output: RetrievalPlan

{
  "clean_query": "sick leave carry forward limit policy",
  "k": 8,
  "notes": [
    "User asked for policy limit",
    "Prefer short answer (from memory)"
  ]
}

Planning responsibilities (minimum): rewrite the query into a searchable form, set k, and optionally add notes that help answer formatting or retrieval focus.

3) Agentic RAG Loop (2-pass)

The Agentic RAG loop executes the plan, checks if context is sufficient, and refines once if needed. 

Algorithm (max 2 iterations)

Input: RetrievalPlan plan

1) Retrieve context using plan.clean_query (text-only)
2) Evaluate sufficiency:
   - If SUFFICIENT → synthesize answer with citations → return
   - If NOT SUFFICIENT → produce refined_query
3) Retrieve again using refined_query
4) Synthesize answer with citations (even if partial) → return

Evaluator: Sufficiency Check (Required Format)

The evaluator decides whether the retrieved context is enough to answer without guessing. Return a small JSON object like this: 

{
  "sufficient": false,
  "missing": [
    "The specific clause that defines the carry-forward limit"
  ],
  "refined_query": "carry forward limit sick leave clause HR policy",
  "confidence": 0.62
}
Guideline: Make the evaluator strict enough that iteration 2 happens sometimes, but not so strict that it always loops. A simple heuristic: require at least one chunk that directly states the answer.

Retrieval Output and Citations (Chunk IDs)

Keep citations simple and deterministic. When you retrieve chunks, assign IDs in order: C1..Ck. Store their source metadata in the trace.

Sample retrieval printout (text-only)

Retrieved Chunks:
[C1] (source=HR_Policy.pdf, page=3) "Sick leave may be carried forward up to 12 days..."
[C2] (source=HR_Policy.pdf, page=2) "Eligibility: employees with 6 months tenure..."
[C3] (source=Leave_FAQ.docx)       "Carry forward applies at year-end close..."

Sample final answer with citations

Answer:
Sick leave can be carried forward up to 12 days at the end of the leave year. [C1]
Eligibility conditions apply (e.g., tenure requirements). [C2]

Tip: if you rerank or dedupe, assign chunk IDs after your final selection and pass that exact ordered list to synthesis, so citations remain consistent.

Trace and Logging (Professional Audit Trail)

Your system should produce a trace.json per user query. This audit trail supports debugging, evaluation, and clear demonstrations. 

{
  "run_id": "2026-02-24T11-30-12Z_7f3a",
  "user_message": "What is the sick leave carry forward limit?",
  "memory_summary_before": "User is asking about leave policies; prefers concise answers.",
  "retrieval_plan": {
    "clean_query": "sick leave carry forward limit policy",
    "k": 8,
    "notes": ["Prefer concise"]
  },
  "iteration_1": {
    "query": "sick leave carry forward limit policy",
    "retrieved": [
      {"chunk_id": "C1", "source": "HR_Policy.pdf", "page": 3},

Minimum requirement: include the plan, evaluator verdict, and citation mapping. Additional fields are optional.

Required Test Prompts (Run These)

These prompts exercise memory, retrieval, and the 2-pass loop. Adapt them to your corpus.

  • Policy fact: “What is the sick leave carry forward limit?”
  • Ambiguous or multi-hop: “Explain sick leave carry forward with an example.”
  • Follow-up using memory: “Now summarize that in 2 lines.”

Stretch Goals (Optional)

  • Clarification path: Front Agent asks one clarifying question if the query is underspecified.
  • Reranking: rerank retrieved chunks before synthesis (keep citations stable).
  • UI: Streamlit/Gradio chat interface with a “Show Trace” panel.

Common Issues and Quick Fixes

  • Evaluator always says “sufficient”: require a direct statement chunk (not just “related”).
  • Evaluator always says “insufficient”: reduce strictness; allow partial answers with a limitation note.
  • Refined query gets worse: merge queries (refined = original + missing terms) instead of replacing.
  • Citations don’t match: assign chunk IDs after final selection (post-rerank) and pass that list to synthesis.
